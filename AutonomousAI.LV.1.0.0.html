$ cat what_changed.md
What's real now, in live mode:
  • Phase 4 (Execute) makes the model write a complete, runnable, single-file HTML product — new build, or a real enhancement of whatever you paste into "existing product to enhance."
  • That output is genuinely rendered in a sandboxed iframe and monitored for real window.onerror / unhandled-rejection events — not asked about, actually triggered by actually running the code.
  • Phase 5 (Verify) combines Claude's honest grading with that real signal: any actual runtime error forces a fail, regardless of what the model or the quality score says. This is a hard override, not a suggestion to the model.
  • Phase 6 (Reflect) receives the real captured error messages, not a guess.
  • A failed cycle's product becomes the input to the next cycle's Execute — the agent is iterating on its own actual output, not starting over.
  • Memory persists in localStorage across reloads and runs; recalled failure/knowledge/strategy entries are passed into Understand/Plan/Execute on every future run.
  • Reflect now retrieves debugging history by actual content: known_failure_patterns is a real keyword search of failure memory against this cycle's actual error text (not just "the last 5 failures"), and Execute now receives those recalled failure patterns too — so cross-run debugging knowledge reaches code generation, not just the plan.
  • Deployment is real: with a GitHub token, "deploy now" (or auto-deploy on release) calls the actual GitHub REST API to create/update a repo, commit the product as index.html, and enable GitHub Pages — you get back a real public URL.
  • The progress bar reflects actual phase transitions (updated from inside runPhaseNode, the same function that drives the diagram) — it is not a timer or an estimate.
  • "Save key" notifications only fire after reading the value back out of localStorage to confirm the write actually happened — and say "saved locally in this browser," never "uploaded," because nothing is uploaded to any server or database.
  • Data feed is real, not filename-based guessing: PDFs are sent to Claude as native document content blocks and read by the model directly. Word/PowerPoint/Excel/zip files are unzipped and their XML parsed for real, entirely in your browser — a from-scratch ZIP central-directory reader plus the browser's own DecompressionStream("deflate-raw") for compressed entries, then real DOMParser XML parsing to pull text. This was tested against synthetic docx/pptx/xlsx archives with mixed compression methods, split text runs, shared-string tables, and inline strings before shipping — not just checked for syntax errors.
  • Known limits of the data feed, stated plainly: docx extraction is body text only (no headers/footers/tables-as-structure/images); pptx is slide text only (no speaker notes/images); xlsx caps at 200 rows per sheet and shows formulas as their last cached value, not the formula itself; generic .zip only extracts members with text-like extensions, everything else is listed by name and size only; encrypted or unusually-compressed ZIP entries are reported as unreadable rather than silently skipped. The one-time "process attachments" summary call is itself an LLM output, so treat it as a well-grounded summary, not a guaranteed-complete transcript of the file.
  • Execute now self-corrects once before failing: if a build attempt comes back with no usable HTML (empty reply, or the model asked a question instead of building), it gets exactly one automatic retry with a corrective instruction quoting what went wrong — visible live in the console log, not just in the final error. If it still fails, the error now reports the API's actual stop_reason and content-block shape instead of a generic message, and correctly reports "reply was empty" instead of silently hiding that diagnosis (an earlier bug: an empty string is falsy in JS, so the old code's result._raw ? check skipped showing the hint exactly when it mattered most).
  • The RELEASE_COMPLETE outcome banner no longer hides deploy failures: previously, if auto-deploy was on and the build passed but the GitHub push failed, the banner still said a plain success with no indication anything was wrong — the deploy error only lived in a small status line. It's now part of the outcome banner itself, in red, with the real error.
  • GitHub is now a verified connection, not a blind token field: clicking "connect" (or loading a saved token on page reload) makes a real GET /user call to GitHub's API and shows the actual authenticated username on success, or the actual rejection reason on failure — before you ever try to deploy anything.
  • The brand mark in the header is a real Canva design, not a placeholder: generated via the actual Canva connector (4 real candidate logos, one materialized into a real Canva design). I could not embed the exported image directly into this file — I tested it, and both this sandbox's network egress and the web-fetch tool reject Canva's export domain, confirmed by an actual 403 host_not_allowed, not assumed. Rather than hardcode the signed export URL (which expires in a few hours and would silently break), the header links to the permanent Canva design page instead.
  • The logo was regenerated to match the light theme: the original was explicitly prompted for a dark navy background, which no longer matched anything in the app after the light-theme conversion. The new one ("Dynamic Loop Logo in Deep Teal with Indigo Accent") was generated using the actual shipped hex values (#0A7267 teal, #5A48D6 indigo) rather than the old bright dark-theme teal, so it's consistent with the real palette instead of a leftover mismatch.
  • Visual system merged with the Canva-designed reference build: palette, fonts (DM Sans for prose, Space Mono for technical/data elements — the same split the Canva file itself used), icons (real Lucide icons replacing hand-drawn SVGs on every primary button), and a real "motion stage" animation adapted from that file's design. None of the merged file's actual logic was used — it had zero API calls and a fixed-timer fake build sequence, documented in an earlier QA pass. Only its visual language was carried over.
  • Colors were re-derived from real contrast math, not copied: Canva's own palette measured as low as 1.7:1 for cyan and lime as text on white — unreadable. Deepened variants were computed and verified (5.4–6.2:1 across the board) before shipping, following the exact same discipline as the earlier dark→light conversion. The bright originals (cyan, lime) are kept for glows/fills/dots only, mirroring a pattern Canva's own file already used in one place (a hardcoded deep green for success text, separate from the bright lime used for fills) — that consistency was verified, not assumed.
  • The motion stage reflects real state, not decoration: its "running" animation only activates during an actual live/demo run (the same disabled flag that locks the form), and its status line and progress fill are driven by the exact same real phase-transition data the text progress bar already used — no separate fake timer.
  • Two real bugs found and fixed while doing this merge: a duplicate CSS rule (header h1 .prompt defined twice) was silently cancelling the intended purple accent on the header's $ symbol — now fixed. And switching the base font from monospace to DM Sans would have silently stripped the monospace styling from every log line, table cell, node label, badge, and memory card (none had their own explicit font-family, they were all just inheriting from body) — explicit font-family:var(--mono) was added back to all 13 of those container rules so the technical areas keep their intended look.
  • Image uploads support the 4 real formats Claude's vision API accepts (JPEG/PNG/GIF/WebP, confirmed against current Anthropic docs before implementing — not "all image formats," which was the literal request), sent as native image content blocks in the same real ingestion call PDFs already use. .jfif is also accepted since it's registered under the same image/jpeg media type, not a separate codec. Genuinely unsupported formats (BMP, TIFF, HEIC, AVIF) are rejected with a clear message rather than silently failing.
  • Fixed a real "empty response" bug: extended thinking is auto-enabled by default on some current models, and thinking tokens count against max_tokens — a complex Execute call could burn its entire budget on internal reasoning and return zero actual output text (the exact reported failure: stop_reason: max_tokens, one thinking content block, no text block). Every API call now explicitly sends thinking: {type: "disabled"}, with a fallback that retries without the field if a given model rejects it outright. Verified against three scenarios, including a direct reproduction of the reported bug, before shipping.
  • Fixed "works in preview, breaks when deployed or opened for real" — the preview iframe's sandbox was allow-scripts only, missing allow-forms. If a generated product used a <form> whose submit handler didn't call event.preventDefault(), the sandbox silently blocked that submission in preview (looked fine), while a real deployment or a locally-opened file has no such restriction — the form would actually submit, causing a full page reload that wipes all state the instant someone used it. Three real fixes, not one: the sandbox now includes allow-forms so preview behavior actually matches deployed reality instead of hiding this bug class; the injected monitor now listens for beforeunload to catch the navigation attempt itself, and also auto-clicks the first 20 buttons on the page as a smoke test, since a bug that only manifests on click was never going to be caught by a load-only check; and the Execute prompt now explicitly instructs against generating this pattern in the first place. Verified with 4 tests run in a real simulated DOM (not just syntax-checked) — including a direct reproduction of an un-prevented form submit, confirmed caught.
  • System check — a new panel that runs real tests, not a canned checklist: browser capability detection (DecompressionStream, DOMParser, FileReader), a genuine localStorage write-then-read-back, and a real end-to-end run of the sandboxed-iframe pipeline (the exact mechanism Execute/Verify use) with a real throwaway test page. The API checks are real network calls — GitHub's is free, Anthropic's is opt-in since it spends a few real tokens.
  • Existing-product upload: the "existing product to enhance" field previously only accepted pasted text. It now has a real Upload button and a process attachment button that runs the exact same checkBasicSanity() check the real product-generation pipeline uses — a genuine validation, not a scripted "always confirmed" message. Note on the native file-picker label some browsers show (e.g. "Pilih File" in Indonesian-locale browsers, "Choose File" in English): that text comes from the browser/OS itself, not this page, so it can't be renamed directly — the fix was to hide the native input entirely and drive it from a custom "Upload" button whose label is fully under this page's control.
  • Max phase per cycle — a new setting (5–10, default 10) that caps how far a FAILED cycle proceeds into the learning arc before moving on. Phases 1–5 always run in full (there's no real outcome without completing Verify), so this can't go below 5. Lower values trade self-correction depth for speed/cost: at 6, only Reflect runs; at 9, everything except Remember runs — meaning nothing from that cycle gets persisted to memory, which is real and disclosed, not silently dropped. Verified with boundary tests at 5/6/7/9/10 against the actual shipped code, confirming exactly the right phases run (and no more) at each level, that memory is only written at 10, and that a real lesson (not a placeholder) is recorded whenever Learn actually ran. This shares the existing "save settings" button rather than getting a duplicate one, since it's a settings field like any other.
  • Quality threshold now genuinely reaches 100% — it was capped at 99 in the slider's own max attribute, a plain oversight. Also flagged: demo mode's scripted score formula tops out at 99 by design, so setting the threshold to 100% will make demo mode fail every cycle — that's disclosed inline now rather than left as a silent mystery. Live mode is unaffected, since a real judgment call can genuinely return 100.
  • Deploy now commits a .nojekyll file alongside the product: GitHub Pages runs everything through Jekyll by default, which can silently mangle or fail to build a plain static HTML/JS file that was never meant to be a Jekyll site. Missing this was the actual cause of an earlier real bug report ("deployed but the page doesn't open").
  • Deploy status now reflects GitHub's real build status, not just "did a URL get returned": after committing, it polls the Pages API for the actual status field (built / building / errored) instead of declaring success the moment a URL exists — which was always premature, since that URL exists before anything has actually built. A still-building or errored result now shows as such, in the outcome banner and the deploy panel, instead of claiming "live" prematurely.
  • The max-cycles cap was silently overriding user input — fixed: it was hardcoded to 5 in both the input field and the JS clamp, with no indication that anything typed above 5 was being ignored. It's now capped at 20 (a real limit — each cycle can make up to ~8 real API calls if it fails, so an unbounded count risks runaway cost/time), and if your input actually gets adjusted, it now says so out loud, in the log and as a toast, and updates the field to show what will really run — never silent again. The 10-phase structure itself (Understand→Remember) is not a configurable count; it's the fixed architecture of one cycle, unrelated to how many cycles you run.
  • "Save settings" now persists every parameter field (goal, constraints, existing product, max cycles, threshold, force-fail, fast mode, model, repo owner/name, auto-deploy) as one unit in localStorage, verified by reading the value back before confirming — same discipline as the API key and GitHub token saves. It auto-restores on page load, including re-syncing the threshold percentage label, not just the slider's raw value. The API key and GitHub token deliberately stay on their own separate save/remember controls, since bundling secrets in with everything else would make them harder to clear independently.
  • Icon/field redesign — Canva was genuinely used, with an honest caveat: a real style-reference design was generated and materialized via the Canva connector (view it here). But I have no way to fetch or view Canva's rendered output myself — the same sandbox restriction from the logo — so unlike the logo (a standalone thing you can look at), I couldn't use it as literal visual input the way "coordinate on a redesign" implies. The actual redesign below was implemented directly from the brief (simple/techie/professional/modern), not copied from the Canva output, and I have not visually rendered the result myself either — only validated it structurally. What changed: checkboxes are now custom toggle switches (pure CSS, zero JS/behavior change — .checked still works identically); the threshold slider has a custom glowing thumb matching the accent color instead of the browser default; every inline icon's stroke-width was unified (was a mix of 1.3/1.6, now a consistent 1.5); and small monochrome icons were added to the 11 most-used field labels for scannability.
  • Switched from dark to light theme, and the old colors were not just recolored — they were re-derived with real contrast math. The person then uploaded the actual Canva design image, which I could view directly (their upload, not a fetch on my end) — a dark navy timeline infographic with a teal-and-purple accent pairing and bold pill/badge treatment. Since the instruction was explicitly to avoid dark theme, I didn't copy its background — I extracted that teal+purple accent language and rebuilt it on white. The old accent colors (teal #49D3C4, amber #F2A65A, green #5FDD8E, red #F1715F) were tuned for a near-black background and would have had contrast ratios of roughly 1.6–2.9:1 as text on white — unreadable. Every semantic color was recalculated against real WCAG relative-luminance math until it cleared 4.5:1 on both the page background and panel surfaces; final measured ratios are 5.46–6.34:1 across teal/amber/green/red/purple, verified against the actual shipped :root values, not just the intended ones. The primary button's text also changed from dark-on-teal to white-on-teal after the same check showed dark text dropping to 2.91:1 at the gradient's deep end. The new purple (--gate, a direct nod to the reference image's purple "Overview" label) now colors the header's prompt symbol, and the version badge became a solid bright-teal pill echoing the reference's badge treatment.
What's still limited, honestly:
  • The HTML "parse validity" check is weak — browsers auto-correct almost any HTML, so it rarely catches anything. The real teeth come from actually running the JS and catching real errors, not from HTML validation.
  • Verify is still one LLM-as-judge pass on top of the real error check, not a full test suite — a subtly wrong-but-error-free product can still pass.
  • Deploy assumes the target repo's default branch works with Pages (usually main) and that your token has the right scope; it does not create a private repo or handle organization-owned repos.
  • No API key = nothing runs live, and no GitHub token = nothing deploys. Neither is faked as a fallback.
