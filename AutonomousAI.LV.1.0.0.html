$ cat what_changed.md
What's real now, in live mode:
  • Phase 4 (Execute) makes the model write a complete, runnable, single-file HTML product — new build, or a real enhancement of whatever you paste into "existing product to enhance."
  • That output is genuinely rendered in a sandboxed iframe and monitored for real window.onerror / unhandled-rejection events — not asked about, actually triggered by actually running the code.
  • Phase 5 (Verify) combines Claude's honest grading with that real signal: any actual runtime error forces a fail, regardless of what the model or the quality score says. This is a hard override, not a suggestion to the model.
  • Phase 6 (Reflect) receives the real captured error messages, not a guess.
  • A failed cycle's product becomes the input to the next cycle's Execute — the agent is iterating on its own actual output, not starting over.
  • Memory persists in localStorage across reloads and runs; recalled failure/knowledge/strategy entries are passed into Understand/Plan/Execute on every future run.
  • Reflect now retrieves debugging history by actual content: known_failure_patterns is a real keyword search of failure memory against this cycle's actual error text (not just "the last 5 failures"), and Execute now receives those recalled failure patterns too — so cross-run debugging knowledge reaches code generation, not just the plan.
  • Deployment is real: with a GitHub token, "deploy now" (or auto-deploy on release) calls the actual GitHub REST API to create/update a repo, commit the product as index.html, and enable GitHub Pages — you get back a real public URL.
  • The progress bar reflects actual phase transitions (updated from inside runPhaseNode, the same function that drives the diagram) — it is not a timer or an estimate.
  • "Save key" notifications only fire after reading the value back out of localStorage to confirm the write actually happened — and say "saved locally in this browser," never "uploaded," because nothing is uploaded to any server or database.
What's still limited, honestly:
  • The HTML "parse validity" check is weak — browsers auto-correct almost any HTML, so it rarely catches anything. The real teeth come from actually running the JS and catching real errors, not from HTML validation.
  • Verify is still one LLM-as-judge pass on top of the real error check, not a full test suite — a subtly wrong-but-error-free product can still pass.
  • Deploy assumes the target repo's default branch works with Pages (usually main) and that your token has the right scope; it does not create a private repo or handle organization-owned repos.
  • No API key = nothing runs live, and no GitHub token = nothing deploys. Neither is faked as a fallback.
